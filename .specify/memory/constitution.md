# acplatform Constitution

## Core Principles

### I. 메인페이지 기준선 준수 (Main Page Baseline Compliance)
**규칙**: 현재 게시된 메인 페이지 프론트엔드 시안(`design/main-page/Main.dc.html` 및 게시된 아티팩트)의
콘텐츠·정보 구조·인터랙션을 프로젝트의 공식 기준선(baseline)으로 삼는다. 이후 모든 프론트엔드 구현은
이 기준선을 반드시 반영해야 하며, 별도 승인 없이 임의로 대체하거나 누락해서는 안 된다.
**이유**: 이미 사용자와 합의된 메인 페이지 시안이 존재한다. 이를 무시하고 새로 설계하면 기존 합의가
무효화되고 팀 간 기준이 흔들린다.
**검토 기준**: 구현 결과물이 기준선 시안의 섹션 구성(헤더, 히어로+검색, 공고 리스트, 이용방법 4단계,
특징 하이라이트, 내 문서함, CTA, 푸터)과 핵심 인터랙션(검색·카테고리 필터, 4단계 작성 마법사, 다운로드
버튼)을 빠짐없이 포함하는지 확인한다. 기준선에서 벗어난 변경은 사유가 PR에 명시되어야 한다.

### II. 명세 범위 엄수 (No Unspecified Features)
**규칙**: spec.md·plan.md·tasks.md에 명시되지 않은 기능, 화면, 옵션을 임의로 추가하지 않는다. 개선
아이디어가 떠오르면 구현하지 않고 제안으로만 남겨 별도 승인을 받는다.
**이유**: 범위 이탈은 일정 지연과 검증되지 않은 복잡성을 낳고, 이해관계자가 승인하지 않은 변경은
서비스의 신뢰성과 관리 가능성을 해친다.
**검토 기준**: 각 커밋·PR의 변경 사항이 대응하는 spec 항목 또는 승인된 tasks 항목과 매핑되는지
확인한다. 매핑되지 않는 변경(명세에 없는 기능 추가)은 반려한다.

### III. 화면 정보구조·디자인 일관성 (Information Architecture & Design Consistency)
**규칙**: 메인 페이지 기준선에서 정의된 정보 구조(섹션 순서, 내비게이션 라벨, 카드·뱃지 패턴)와 디자인
토큰(네이비 프라이머리 + 앰버 액센트 컬러, Noto Serif KR/Noto Sans KR 타이포, 여백·라운드 규칙)을
신규 화면에도 동일하게 적용한다.
**이유**: 여러 화면에 걸쳐 시각적·구조적 일관성이 없으면 사용자가 서비스를 신뢰하기 어렵고, 유지보수
비용이 증가한다.
**검토 기준**: 신규 화면 디자인·구현이 기존 컬러 토큰·폰트·컴포넌트 패턴(카드, 뱃지, 버튼 스타일)을
재사용하는지 확인한다. 벗어난 경우 그 사유가 디자인 문서나 PR에 기록되어 있어야 한다.

### IV. 요구사항-디자인 추적성 (Requirement & Design Traceability)
**규칙**: 모든 구현 TASK는 이를 발생시킨 요구사항(spec 항목 ID)과 디자인 근거(시안 섹션·컴포넌트 또는
디자인 결정 기록)를 명시적으로 인용해야 한다. 근거를 특정할 수 없는 TASK는 착수하지 않는다.
**이유**: 추적성이 없으면 특정 코드가 왜 존재하는지 알 수 없게 되어, 이후 변경이나 감사(특히 규제·공고
요건 대응 시)가 어려워진다.
**검토 기준**: tasks.md의 각 TASK 항목에 "관련 요구사항"과 "디자인 근거" 필드가 채워져 있는지, PR
설명에 동일한 근거가 인용되는지 확인한다.

### V. 실제 나라장터 API 연동 원칙 (Live Procurement API Integration)
**규칙**: 나라장터 공고 조회 기능은 목업·더미 데이터가 아니라, 사전에 발급받아 보유하고 있는 실제
인증키를 사용해 공공데이터포털 나라장터 API에 연동하여 실 공고문을 조회하는 것을 목표로 한다. 인증키는
소스 코드나 저장소에 하드코딩하지 않고 환경변수·시크릿 관리 체계를 통해 주입한다.

**양식 폴백 체인 원칙**:
나라장터 공고마다 안전보건관리계획서 샘플이 첨부되어 있지 않으므로, 서비스는 다음 우선순위를 따라
사용자에게 양식을 제공해야 한다:

1. **공고 첨부 샘플**: API에서 조회한 공고에 첨부 파일이 있으면 이를 파싱해 양식 필드를 추출
2. **발주처 표준 양식**: 발주처별로 사전 등록한 최적화된 기본 양식 템플릿 사용
3. **범용 기본 양식**: 서비스 자체에 정의된 건설업 표준 안전보건관리계획서 기본 양식 사용
4. **회원 업로드 양식**: 위 세 경로가 모두 불가능하면 회원이 직접 양식 파일(PDF/DOCX/HWP)을 업로드해
   시스템이 파싱. 파싱 실패 시 수동 입력 모드 제공

이 체인을 통해, 공고 다양성에 관계없이 사용자는 항상 계획서 작성을 시작할 수 있게 된다.

**발주처별 낙찰/진행상태 판단 폴백 체인**:
안전보건관리계획서는 입찰이 종료된(낙찰 확정된) 공사를 대상으로 작성해야 한다. 그러나 발주처마다
제공하는 오픈API의 데이터 범위가 다르므로(최종 낙찰자 정보까지 주는 곳도 있고, 개찰 결과까지만 주는
곳도 있고, 그마저도 없는 곳도 있음), 신규 발주처를 연동할 때는 다음 우선순위를 따라 "이미 종료된
공고"를 판단한다:

1. **최종 낙찰자 확정 정보**: 낙찰자명·낙찰금액·낙찰(확정)일자를 제공하는 API가 있으면 이를 사용해
   `awarded=true`로 표시 (예: 조달청 낙찰정보서비스, 한전 `progressState=Final`)
2. **개찰결과 1순위 업체 정보**: 최종 낙찰자 확정 API가 없지만 개찰결과(1순위 투찰업체) API가 있으면
   이를 차선책으로 사용 (예: LH 개찰정보(개찰결과정보))
3. **입찰공고 마감일 기준**: 위 두 경로가 모두 없으면, 입찰공고 자체의 마감일이 오늘 기준 과거이고
   최근 30일 이내인 공고만 노출 (예: 방위사업청)

각 발주처 연동 시 이 세 단계 중 어디까지 지원 가능한지 실제 API 응답으로 확인한 뒤 구현하며, 이미
확정된 결과(1·2단계)는 발행일이 오래됐더라도 "최근 30일" 마감일 필터에서 제외하지 않는다(확정 자체가
접수/개찰로부터 수개월 걸릴 수 있으므로).

**이유**: 실제 공고 데이터 없이는 서비스의 핵심 가치(공고별 맞춤 계획서 자동화)를 검증할 수 없으며,
실 연동이 최종 목표다. 또한 모든 공고에 샘플이 있지 않으므로, 폴백 체인을 통해 서비스 가용성을 극대화해야 한다.
발주처마다 API 데이터 범위가 다르므로, 낙찰/진행상태 판단도 동일한 방식의 폴백 체인이 필요하다.

**검토 기준**: 
- API 연동 구현이 실제 인증키로 호출 성공(정상 응답, 실제 공고 데이터 반환)을 재현 가능한 테스트나 스크립트로 증명
- 인증키가 소스 코드·로그·커밋 이력에 노출되지 않았는지 확인
- 양식 선택 화면 구현이 4가지 폴백 경로를 모두 처리 가능하고, 사용 가능한 옵션만 표시하는지 검증
- 파일 파싱 로직(PDF/DOCX/HWP)이 다양한 포맷 견디기(resilience)와 실패 모드(수동 입력)를 제공하는지 확인
- 신규 발주처 연동 시 낙찰/진행상태 판단이 3단계 폴백 체인 중 어느 단계에 해당하는지 코드 주석/문서에 명시

### VI. 원칙 확장 가능성 (Open for Amendment)
**규칙**: 본 원칙 목록은 폐쇄적이지 않다. 프로젝트 진행 중 필요에 따라 새로운 원칙을 추가하거나 기존
원칙을 개정할 수 있다. 단, 추가·개정은 반드시 Governance 절차(제안 문서화 → 책임자 승인 → 버전 갱신)를
거친다.
**이유**: 초기 단계에서 모든 governance 요구를 예측할 수 없으므로, 헌법 자체가 점진적으로 성장할 수
있어야 한다.
**검토 기준**: 새 원칙 추가·개정 시 Sync Impact Report와 버전 번호가 함께 갱신되었는지, 기존 원칙 번호
체계가 임의로 재배치되지 않았는지 확인한다.

## 기술 및 통합 제약
<!-- Technology & Integration Constraints -->

생성 문서 출력은 PDF와 DOCX 두 형식을 모두 지원해야 하며, 두 형식 간 내용과 서식의 일관성을 보장해야
한다. 공고 첨부파일 파싱(한글·워드·PDF 등 다양한 포맷)은 실패 시 사용자에게 수동 확인을 요청하는 대체
경로(fallback)를 반드시 제공해야 한다. 나라장터 API 연동은 Principle V를 따른다.

## 개발 워크플로
<!-- Development Workflow -->

모든 기능은 Spec Kit 절차(specify → clarify → plan → tasks → implement)를 거쳐 개발한다. tasks.md의
각 항목은 Principle IV에 따라 요구사항과 디자인 근거를 명시해야 병합 가능하다. 핵심 로직(요구사항
매칭, 문서 생성, API 연동) 변경은 코드 리뷰 통과를 병합 조건으로 한다.

## Governance

본 헌법은 프로젝트의 다른 모든 관행에 우선한다. 개정은 다음 절차를 따른다: (1) 변경 제안과 근거를
문서화, (2) 프로젝트 책임자의 승인, (3) 영향받는 템플릿·가이드 문서 동기화. 원칙 목록은 Principle VI에
따라 폐쇄적이지 않으며 추가·개정될 수 있다. 버전은 시맨틱 버저닝을 따른다 — 원칙의 제거나 하위 호환
불가능한 재정의는 MAJOR, 원칙 추가나 실질적 내용 확장은 MINOR, 문구 수정이나 명확화는 PATCH. 모든 PR과
리뷰는 본 헌법 준수 여부를 확인해야 하며, 복잡성 증가는 반드시 정당화되어야 한다.
